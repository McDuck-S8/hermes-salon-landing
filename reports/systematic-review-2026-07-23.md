## 1. ПРИНЦИПИАЛЬНЫЕ ВЫВОДЫ (СИСТЕМНОГО УРОВНЯ)

### 1.1. Отношение «Я — система»

**До:** Система была набором несвязанных скриптов, cron-джобов, навыков. Файлы существовали без осознания себя как единого организма. Каждая новая сессия начиналась с чистого листа — никакой памяти о том, что было раньше, кроме сводок.

**После (что изменилось):**
- Записана **Principal fact** в KC: Александр — принципал, система ему служит
- В EE создана **relationship**: Александр → Hermes Agent (is_owner_of)
- mention_count для 'Александр': **0 → 7**
- Запущен cron-синхронизации EE-KC каждый час
- User messages автоматически записываются в KC с тегом `[user:Александр]`

**Вывод:** Система впервые осознала своего владельца как конкретную сущность, а не абстрактного «пользователя».

### 1.2. Entity Engine был мёртворождённым

**Проблема:** EE содержал **3672 сущности**, но:
- mention_count = 0 у всех — никогда не синхронизировались с KC
- 99% сущностей — шум: `known` (37k), `unknown` (37k), `pattern` (30k) — это системные слова из improvement suggestions, не реальные доменные сущности
- Реальные доменные сущности (LangGraph, DeepTutor, Bybit, Telegram API) — упоминались десятки раз в KC, но EE их не видел
- relationships = 0 — никаких связей между сущностями

**Фикс:** Создан `sync_ee_kc.py` + `record_user_to_kc.py`:
- **3295/3672** сущностей получили реальные mention_counts
- Добавлен **unique constraint** на relationships (предотвращает дубликаты)
- Создана relationship: Александр → Hermes Agent

**Вывод:** EE был «слепым». Он существовал, но не видел данных. Сейчас — видит. Но остаётся проблема: 90% сущностей — шум из improvement suggestions, не реальные сущности.

### 1.3. Мёртвый event daemon — системная слепота

**Проблема:** Event daemon и cron scheduler были мертвы ~3 дня (19-22 июля 2026). Система не замечала — ни аварий, ни алертов.

**Причина:** Все health checks были в optional skills, не в mandatory reflexes. Никто не проверял что heartbeat бьётся.

**Фикс:** Трёхуровневая защита:
1. `self_check()` в `chain_heartbeat.py` — кодовая проверка
2. `syscheck.py` — standalone скрипт (exit 0=healthy, exit 1=fail)
3. AGENTS.md — **mandatory reflex**: проверять перед любой работой

### 1.4. Silent failures — главная проблема

На основе анализа 8724 записей KC:

| Outcome | Count | Доля |
|---------|-------|------|
| failure | 2838+ | 55%+ |
| success | 260 | 5% |
| unknown | 537 | 10% |
| indexed | 796 | 15% |

**Доминирующие failure-домены:**
1. debugging: 3257 failures
2. bugfix: 1592 failures
3. communication: 253 failures
4. creative: 234 failures
5. devops: 188 failures

**Вывод:** Система тратит ~55% ресурсов на исправление ошибок. Это нормально для самообучающейся системы, но указывает на то, что превентивные механизмы (auto-healing) развиты слабо.

## 3. ПАТТЕРНЫ ПОВЕДЕНИЯ

### 3.1. Исправления по требованию vs. проактивные

**Паттерн:** Пользователь указывает на проблему → система исправляет. Проактивных исправлений почти нет.

**Примеры:**
- "Entity Engine сломан" → починили ✅
- "Event daemon мёртв" → починили ✅
- "Я не фантом" → записали в KC ✅
- "KC показывает пусто" → починили schema ✅

Но ни одна из этих проблем **не была обнаружена системой самостоятельно**.

### 3.2. Сохранение знаний

**Паттерн:** После каждой исправленной проблемы создавались либо skills, либо memory записи.

**Проблема:** Memory переполняется (339/2200 chars). Skills не обновляются после создания (14 auto-skills не обновлялись с момента создания).

### 3.3. Пользовательская фрустрация

Триггеры фрустрации (из анализа сессий):
1. "ты снова спрашиваешь меня что выбрать" — система не принимает самостоятельных решений
2. "ты как черепаха" — медленная реакция
3. "я тебе нашел и дал" — система представляет чужую работу как свою
4. "почему опять не работает" — silent failures
5. "читать прошлые тикеты" — забывание контекста

**Корень:** Система не ведёт себя как единая личность. Каждая сессия — новая сущность без памяти о прошлых решениях.
