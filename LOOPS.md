# LOOPS.md — Замкнутые петли Autonomous Income System

Формальное описание архитектуры агента как набора замкнутых петель.
Каждая петля — самодостаточный цикл: триггер → исполнение → результат → стоп-критерий.
Петли передают управление друг другу через события и данные.

**Создано:** 2026-06-28

---

## LOOP 1: PROCEDURAL (Рефлексы)

**Название:** Procedural Reflex Loop

**Триггер:** Сенсорное событие — сеть упала, порт мёртв, gateway недоступен,
cron в error, disk > 80%, memory > 80%, API ключ истёк, процесс завис.

**Частота:** По событию (event-driven) или по таймеру (every 60s если event_daemon активен).
Нет фиксированного интервала — только реакция на аномалию.

**Исполнитель:** procedural_executor.py + event_bus.py + event_daemon.py
- event_daemon.py мониторит сенсоры (ping, port check, process check, disk, memory)
- event_bus.py классифицирует событие и маршрутизирует в procedural_executor.py
- procedural_executor.py выполняет ДЕТЕРМИНИРОВАННУЮ цепочку БЕЗ LLM

**Выход:**
- Результат действия → cache/procedural_feedback.jsonl
- Критические алерты → cache/ALERTS.md
- Если рефлекс не помог → эскалация в Loop 2 (Linial)

**Критерий остановки:**
- Цепочка выполнена успешно → стоп
- Цепочка провалилась 3 раза → стоп, эскалация
- Сенсорное событие больше не активно → стоп
- Агент не запущен → стоп

**Паттерны (из procedural_executor.py):**
```
Порт мёртв → убить процесс → перезапустить → проверить
Gateway не найден → залогировать → эскалировать
Disk > 80% → найти большие файлы → залогировать
Memory > 80% → найти процессы → залогировать
API ключ истёк → рефреш → fallback провайдер
```

## LOOP 2: LINEAL (Целевая)

**Название:** Linear Goal Execution Loop

**Триггер:**
- Ручная команда: "сделай X"
- Автономное решение autonomous_agent.py (scoring матрица, лучший кандидат)
- Эскалация из Loop 1 (рефлекс не справился)
- Новая цель в goal_queue.json

**Частота:** По требованию. Не циклическая — одна цель = один прогон.

**Исполнитель:**
- autonomous_agent.py — принятие решения (29 кандидатов → scoring → выбор)
- goal_executor.py — декомпозиция цели → шаги → выполнение
- goal_queue.py — управление очередью целей
- Все доступные модули: posting/, salon_ai_bot.py, tg_cpa_poster.py и др.

**Выход:**
- Результат → goal_queue.json (статус: completed/failed)
- Артефакты → файлы, скрипты, сообщения
- Feedback → cache/feedback_store (если существует) или DECISION_LOG.md
- Успешный результат → Loop 3 (параллельная работа) или пользователю

**Критерий остановки:**
- Цель достигнута (результат подтверждён) → стоп
- Цель провалилась (3 попытки) → стоп, пометить failed
- Блокирующая зависимость (нужен другой модуль) → стоп, ждать
- Нет ресурсов (API ключ, сеть, время) → стоп, эскалация

## LOOP 3: PARALLEL (Многопоточная)

**Название:** Parallel Multi-Department Loop

**Триггер:**
- Автономный агент принял решение выполнять несколько независимых задач
- Cron job запускает параллельные процессы
- Делегирование через delegate_task (subagent'ы)

**Частота:** Параллельно с Loop 2. Нет своей частоты — наследует от родительской петли.

**Исполнитель:**
- delegate_task — спавн субагентов (до 3 параллельных)
- Каждый субагент = изолированный контекст + терминал + инструменты
- Каждый модуль работает независимо:
  - Posting pipeline (tg_cpa_poster.py)
  - Salon bot (salon_ai_bot.py)
  - Monitoring (network_watchdog.py, bot_monitor.py)
  - Crystal learning (crystal/core.py)
  - Каналы (self_improve_from_channels.py)

**Выход:**
- Каждый субагент → свой результат (саммари)
- Суммарный результат → Loop 2 (обновление статуса цели)
- Критические ошибки → Loop 1 (рефлексы)
- Успешные паттерны → Loop 4 (стратегия)

**Критерий остановки:**
- Все субагенты завершились → стоп
- Timeout (5 минут на субагента) → стоп, логировать timeout
- Родительская сессия закрыта → стоп (субагенты теряются)
- Субагент вернул ошибку → стоп, логировать, не блокировать остальных

**Ограничения:**
- Максимум 2 уровня вложенности (orchestrator → worker)
- Субагенты НЕ могут: clarify, memory, send_message
- Субагенты НЕ помнят контекст родителя (передавать через context)

## LOOP 4: STRATEGIC (Стратегическая)

**Название:** Strategic Priority Review Loop

**Триггер:**
- Периодический cron (ежедневно или после N завершённых целей)
- Ручная команда: "пересмотри приоритеты"
- Crystal self-learning loop завершил цикл observe → diagnose → will → execute
- SELF_AUDIT.md показывает расхождение между действиями и результатами

**Частота:** Eжедневно или по событию (после каждых 5 выполненных целей).
Это НЕ фоновый процесс — это точечное вмешательство.

**Исполнитель:**
- crystal/core.py — self-learning: observe → diagnose → will → execute → learn
- self_improvement_loop.py — анализ сессий → извлечение уроков
- proactive_engine.py — проактивные предложения
- self_improvement_from_channels.py — обучение из Telegram каналов
- SESSION_ANALYSIS.md → выявление паттернов

**Выход:**
- Обновлённый goal_queue.json (новые цели, удаление мёртвых)
- Обновлённый agent_policies.md (новые правила)
- Обновлённый SELF_IDENTITY.md (изменения в структуре)
- Решения → DECISION_LOG.md
- Удачные паттерны → Knowledge Cube → Loop 2 (автоматическое применение)
- Мёртвые цели → удаление из goal_queue.json

**Критерий остановки:**
- Приоритеты пересмотрены, goal_queue обновлён → стоп
- Нет данных для анализа → стоп
- Self-audit показывает "всё ок" → стоп
- Агент не запущен → стоп

## ВЗАИМОДЕЙСТВИЕ ПЕТЕЛЬ

### Кто кому передаёт управление:

```
┌─────────────────────────────────────────────────────────┐
│                    LOOP 4: STRATEGIC                    │
│              (стратегия, приоритеты, уроки)              │
│                                                         │
│  Вход: опыт из Loop 1-3, Crystal, каналы                │
│  Выход: обновлённые цели и правила                      │
│                                                         │
│  ↓ передаёт новые цели ↓                                │
├─────────────────────────────────────────────────────────┤
│                   LOOP 2: LINEAL                        │
│            (цели → шаги → выполнение)                   │
│                                                         │
│  Вход: цели из goal_queue, команды пользователя          │
│  Выход: результаты, артефакты, feedback                  │
│                                                         │
│  ↓ делегирует параллельные задачи ↓                     │
├─────────────────────────────────────────────────────────┤
│                  LOOP 3: PARALLEL                       │
│          (параллельная работа модулей)                   │
│                                                         │
│  Вход: независимые задачи из Loop 2                     │
│  Выход: результаты субагентов                           │
│                                                         │
│  ↕ обратная связь с Loop 2 (статус задач)               │
├─────────────────────────────────────────────────────────┤
│                 LOOP 1: PROCEDURAL                      │
│            (рефлексы, мониторинг, восстановление)        │
│                                                         │
│  Вход: сенсорные события (сеть, порты, диски)           │
│  Выход: исправление или эскалация в Loop 2              │
│                                                         │
│  ⚡ работает НЕЗАВИСИМО от Loop 2-4                     │
└─────────────────────────────────────────────────────────┘
```

### Кто кого блокирует:

- **Loop 1 блокирует Loop 2:** если сеть мертва — нет смысла выполнять цель
- **Loop 2 блокирует Loop 3:** пока цель не декомпозирована — параллельно нечего
- **Loop 4 блокирует Loop 2:** пока стратегия не пересмотрена — старые цели мусор

### Кто работает независимо:

- **Loop 1 (Procedural)** работает ВСЕГДА, независимо от остальных. Это единственный
  фоновый процесс, который не ждёт разрешения. Он — аварийный режим.
- **Loop 3 (Parallel)** работает независимо друг от друга (субагенты изолированы).
  Один субагент может упасть без влияния на других.

### Порядок запуска при старте агента:

```
1. Loop 1: procedural_executor --status (рефлексы готовы?)
2. Loop 1: reality_gate (сеть, gateway, cron)
3. Loop 4: Crystal (обновить стратегию, если нужно)
4. Loop 2: goal_queue (загрузить активные цели)
5. Loop 2: autonomous_agent (выбрать лучшее действие)
6. Loop 3: delegate_task (выполнить параллельно, если есть задачи)
```

### Цикл обратной связи:

```
Loop 2 (выполнение) → feedback_store → Loop 4 (анализ)
Loop 1 (рефлекс) → ALERTS.md → Loop 4 (анализ)
Loop 3 (субагенты) → session recall → Loop 4 (анализ)
Loop 4 (уроки) → goal_queue.json → Loop 2 (новые цели)
Loop 4 (уроки) → agent_policies.md → Loop 2 (новые правила)
```

## LOOP ENGINEERING — Метрики оптимизации

Каждая петля имеет измеримые параметры:

### Loop 1 (Procedural)
- **Latency:** время от триггера до действия (цель: < 10s)
- **Success rate:** % успешных цепочек (цель: > 80%)
- **Escalation rate:** % эскалаций в Loop 2 (цель: < 20%)
- **False positive rate:** ложные срабатывания (цель: < 5%)

### Loop 2 (Linear)
- **Goal completion rate:** % выполненных целей (цель: > 60%)
- **Time to completion:** среднее время от цели до результата
- **Retry rate:** % целей потребовавших повтора (цель: < 30%)
- **Artifact count:** количество артефактов за сессию

### Loop 3 (Parallel)
- **Concurrency utilization:** среднее количество параллельных задач
- **Subagent success rate:** % успешных субагентов
- **Timeout rate:** % timeout'ов (цель: < 10%)
- **Token efficiency:** токены на результат

### Loop 4 (Strategic)
- **Stale goal removal:** количество удалённых мёртвых целей
- **Policy updates:** количество обновлений agent_policies.md
- **Learning rate:** количество новых паттернов в Knowledge Cube
- **Priority alignment:** % целей соответствующих стратегии

## LOOP ENGINEERING — Компоненты

### 1. Git Worktrees — Изоляция для параллельной работы (Loop 3)

**Триггер:**
- Loop 3 запускает параллельные задачи, требующие независимых файловых систем
- Несколько субагентов работают с одним репозиторием одновременно
- Нужно изолировать экспериментальные изменения от стабильной ветки

**Исполнитель:**
- `git worktree add <path> <branch>` — создание изолированного рабочего дерева
- Каждый субагент получает свой worktree с уникальным путём
- Основной worktree остаётся нетронутым для Loop 2

**Выход:**
- Изолированный каталог с полной копией репозитория
- Отдельная ветка для изменений (feature/worktree-<id>)
- После завершения: merge в основную ветку или удаление

**Критерий остановки:**
- Worktree создан успешно → переход к выполнению задачи
- Ветка уже существует → reuse существующего worktree
- Нет места на диске → стоп, эскалация в Loop 1
- Задача завершена → `git worktree remove <path>`

### 2. Maker-Checker Pattern — Раздельная верификация (Loop 2)

**Триггер:**
- Loop 2 выполняет критические операции (деплой, отправка, изменение конфигов)
- Результат работы нуждается в независимой проверке
- Цель требует двухфазного выполнения: создание → проверка

**Исполнитель:**
- **Maker:** goal_executor.py выполняет основную задачу
- **Checker:** отдельный процесс (или тот же goal_executor в режиме verify) проверяет результат
- Разделение контекста: maker не видит результат checker, checker не видит процесс maker

**Выход:**
- Артефакт от maker → промежуточное хранилище
- Результат проверки: PASS / FAIL / PARTIAL
- Если FAIL → возврат к maker с описанием ошибок
- Если PASS → продвижение в следующую петлю

**Критерий остановки:**
- Checker подтвердил результат → стоп, результат валиден
- Checker обнаружил ошибку → стоп, возврат maker (max 3 цикла maker-checker)
- Timeout проверки → стоп, эскалация
- Оба процесса завершились → стоп

### 3. Maturity Matrix — Оценка текущего уровня зрелости

**Триггер:**
- Loop 4 (стратегическая) запускает периодическую оценку
- Пользователь запрашивает "где мы сейчас?"
- Ключевая метрика упала ниже порога → нужна диагностика

**Исполнитель:**
- Аналитический модуль, читающий метрики из всех петель
- Сравнение текущих значений с целевыми (из секции "Метрики оптимизации")
- Формирование матрицы зрелости по 5 уровням

**Выход:**
| Уровень | Описание | Критерий |
|---------|----------|----------|
| L0 (Chaos) | Нет петель, ручное управление | Loop 1 не работает |
| L1 (Reactive) | Только Loop 1, аварийные рефлексы | success rate > 50% |
| L2 (Goal-driven) | Loop 1+2, есть цели и выполнение | goal completion > 40% |
| L3 (Parallel) | Loop 1+2+3, параллельная работа | concurrency > 1.5 |
| L4 (Strategic) | Все Loop, self-learning, оптимизация | learning rate > 0 |

- Результат → `cache/maturity_assessment.json`
- Рекомендации → следующий шаг для повышения уровня

**Критерий остановки:**
- Матрица рассчитана → стоп, результат в Loop 4
- Недостаточно данных для оценки → стоп, пометить "insufficient data"
- Уровень не изменился с прошлой оценки → стоп, без рекомендаций

### 4. Budget/Token Limits — Лимиты токенов в петлях

**Триггер:**
- Каждая петля при старте проверяет оставшийся бюджет
- Приближение к лимиту → предупреждение
- Достижение лимита → принудительная остановка

**Исполнитель:**
- `token_budget.py` — трекинг потребления токенов по петлям
- Лимиты: Loop 1: 0 LLM (детерминированная), Loop 2: 10K tokens/цель, Loop 3: 5K tokens/субагент, Loop 4: 15K tokens/сессия

**Выход:**
- Текущий баланс → `cache/token_budget.json`
- Предупреждения при 80% использования
- Автоматическая эскалация при 100%

**Критерий остановки:**
- Бюджет исчерпан → стоп, логировать потребление
- Задача завершена до лимита → стоп, записать остаток
- Петля 1 (Procedural) не потребляет токены → без лимита
- Бюджет восстановлен (новый день/месяц) → сброс счётчика

### 5. Human Review Gates — Шлюзы ручного контроля

**Триггер:**
- Операция затрагивает внешние системы (отправка сообщений, деплой, оплата)
- Цель в категории "high risk" (создание аккаунтов, финансовые операции)
- Эскалация из предыдущей петли с пометкой "needs_approval"

**Исполнитель:**
- `human_gate.py` — блокирующий вызов с запросом подтверждения
- Записывает контекст в `cache/pending_approvals.json`
- Ожидает: ручной ввод, Telegram уведомление, или auto-approve (для low-risk)

**Выход:**
- APPROVED → продолжение执行
- REJECTED → стоп, откат изменений
- TIMEOUT (24h) → стоп, пометить "expired"
- PARTIAL → продолжение с ограничениями

**Критерий остановки:**
- Подтверждение получено → стоп,执行 продолжается
- Отклонение получено → стоп, откат
- Таймаут → стоп, уведомление Loop 4
- Повторный запрос после rejection → стоп, requires user intervention

### 6. Skills for Task Parsing — Парсинг задач из внешних источников

**Триггер:**
- Внешний источник (Telegram, email, RSS, API) предоставил новую задачу
- Loop 4 импортирует знания из каналов → нужен парсинг в цели
- Пользователь отправил неструктурированное описание задачи

**Исполнитель:**
- `task_parser.py` — извлечение структуры из текста
- NLP-шаги: определение типа (setup/fix/create/monitor), приоритета, дедлайна
- Валидация формата → `goal_queue.json` совместимый объект

**Выход:**
- Структурированная задача → `goal_queue.json` (новая запись)
- Мета-информация: source, confidence, parsed_at
- Если confidence < 0.5 → пометить "needs_clarification"

**Критерий остановки:**
- Задача распарсена успешно → стоп, запись в goal_queue
- Не удалось извлечь обязательные поля → стоп, пометить "unparseable"
- Источник недоступен → стоп, retry через 5 минут
- Максимум 3 попытки парсинга → стоп, эскалация Loop 4
