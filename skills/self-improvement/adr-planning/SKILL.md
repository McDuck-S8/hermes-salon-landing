# ADR Planning — Architecture Decision Records

## Когда использовать

- **Перед каждым архитектурным выбором**: инструмент, подход, структура, интеграция
- **После изучения нового подхода к планированию**
- **При изменении решения**: создать новый ADR со статусом "supersedes ADR-N"
- **Когда есть ≥2 альтернатив** с разными трейдоффами — ADR фиксирует почему выбрана одна

## Когда НЕ использовать

- Тривиальные выборы (версия библиотеки, нейминг переменной, формат кода)
- Очевидные решения без альтернатив (исправить баг там где он произошёл)
- Временные/экспериментальные изменения (если решение откатится через день — ADR избыточен)

## Формат ADR

```markdown
# ADR-N: Заголовок
Status: proposed | accepted | deprecated | superseded
Дата: YYYY-MM-DD
Supersedes: ADR-M (если заменяет предыдущее)
Source: [что спровоцировало — репозиторий, ошибка, требование]

## Context
- Какая проблема решается?
- Какие ограничения? (бюджет, время, технологии, окружение)
- Какие альтернативы рассматривались?
- Почему они не подошли?

## Decision
- Что выбрано?
- Почему именно это? (главная причина — одна строка)

## Consequences
- Плюсы: что это даёт, что открывает
- Минусы: какие трейдоффы, что это ломает
- Что дальше: следующий шаг
```

## Правила (выучены на практике)

1. **Пиши ДО или СРАЗУ после решения.** Контекст забывается за час. Если пишет агент — записывать в момент принятия решения, а не в конце сессии
2. **Одно решение = один ADR.** Не смешивай несколько решений в одном документе
3. **Указывай статус.** Accepted = активно. Deprecated = больше не используется. Superseded = заменено новым ADR
4. **Ссылайся на другие ADR.** Если решение опирается на предыдущее — укажи `Supersedes: ADR-003`
5. **Храни в `skills/planning/adr/`.** Рядом с другими ADR для связности
6. **ADR не заменяет README.** ADR — почему, README — как

## Связь с другими фреймворками планирования

| Фреймворк | Что даёт | Как сочетается с ADR |
|-----------|----------|---------------------|
| **OKR** | Objectives & Key Results — куда идём? | ADR объясняет *почему* выбрали эти OKR |
| **SMART** | Критерии хорошей цели | Применять к задачам; ADR — к решениям |
| **MoSCoW** | Must/Should/Could/Won't — приоритеты | ADR фиксирует почему что-то стало Won't |
| **RACI** | Кто за что отвечает | ADR может указать кто принимал решение |
| **How-To-Ask-Questions** | Декомпозиция проблемы | Применять *перед* ADR — сначала разбить проблему |

## Пример из этой сессии

```markdown
# ADR-001: Внедрение ADR как практики планирования
Status: accepted

Context: Изучил 5 репозиториев по планированию. Понял что моя слабая точка —
не записываю ПОЧЕМУ принял решение. OKR/SMART — про то ЧТО делать, ADR — про ПОЧЕМУ.

Decision: Внедрить ADR для всех архитектурных решений. Создать навык adr-planning
с шаблоном. Первый ADR — об этом решении.

Consequences:
+ Институциональная память решений
+ Возможность вернуться и понять контекст
+ Фактор принуждения — заставляет думать прежде чем решать
- Дополнительное действие перед каждым решением
- Риск бюрократизации (решение: не писать ADR на тривиальные выборы)
```

## Pitfalls

- **Не писать ADR в конце дня** — детали забыты, качество низкое. Пиши в момент
- **Не делать ADR слишком длинным** — 3-5 предложений на секцию. Если Context на страницу — решение слишком сложное, разбей
- **Не использовать ADR как TODO** — это не план работ, это запись решения
- **Не ретроспективно переписывать ADR** — если контекст изменился, пиши новый со статусом superseded
- **Не смешивать ADR с agent memory** — memory для фактов о пользователе/окружении, ADR для архитектурных решений
