# Socratic Task Breakdown (Разбор задачи по косточкам)

Рекурсивный протокол декомпозиции. Агент не бросается выполнять задачу,
а сначала разбирает её на атомарные шаги через цепочку вопросов.

Синтез подходов: PDCA, Agent Architect Questionnaire, Recursive Decomposition,
Maestro orchestration, Socratic Reasoning Patterns (6 патернов).

---

## Когда запускать

- Задача сформулирована расплывчато («сделай бота», «улучши систему»)
- Задача требует 3+ действий
- Есть неопределённость в требованиях, инструментах, или критериях
- Пользователь явно попросил разобрать задачу

**НЕ запускать** когда:
- Задача атомарна (1-2 шага, всё ясно)
- Пользователь сказал «делай» / «продолжай» / «без вопросов» / «далее»
- Пользователь выразил раздражение от анализа/вопросов/задержек
- В user profile стоит «fix forward», «не анализировать», «executor, not decider»
- Чистый баг-фикс с воспроизводимым сценарием

---

## Алгоритм

```
PHASE 0: Init
PHASE 1: Mission Clarity
PHASE 2: Context & Constraints
PHASE 3: Tool Mapping
PHASE 4: Decomposition Decision (ATOMIC / COMPOSITE / AMBIGUOUS)
PHASE 5: If AMBIGUOUS → ask user → return to PHASE 1
PHASE 6: If COMPOSITE → split into subtasks → recurse (depth+1)
PHASE 7: If ATOMIC → record executable step
PHASE 8: Aggregation → ordered plan
PHASE 9: Verification Gate
OUTPUT: Execution Plan
```

---

## PHASE 0: Init

```
Задача: {task_description}
Глубина рекурсии: 0 (max_depth=5)
Статус: НАЧАЛО
```

---

## PHASE 1: Mission Clarity

Определить ЧТО должно быть результатом (не КАК).

| Вопрос | Цель |
|--------|------|
| Q1: Что конкретно должно быть результатом? | Избежать размытых целей |
| Q2: По каким критериям пойму, что задача выполнена? | Определить Done |
| Q3: Кто будет это использовать/проверять? | Роль и аудитория |

**Выход:** чёткое описание результата + accept criteria.

---

## PHASE 2: Context & Constraints

| Вопрос | Цель |
|--------|------|
| Q4: Какие входные данные нужны? (что есть сейчас?) | Инвентаризация |
| Q5: Какие ограничения? (время, доступы, безопасность, среда) | Boundary conditions |
| Q6: Есть ли существующие паттерны/решения, на которые можно опереться? | Reuse |

## PHASE 2a: Pipeline Trace (мастхэв для системных изменений)

**Перед тем как менять/добавлять компонент — нарисуй цепочку от начала до конца.**

```
[вход] → [шаг 1] → [шаг 2] → ... → [потребитель]
```

Обязательные вопросы:

| Вопрос | Зачем |
|--------|-------|
| Q6a: Кто потребитель результата каждого шага? | Если шаг пишет данные — кто их читает? |
| Q6b: Все ли компоненты цепочки существуют? | Producer без consumer = мёртвая дыра |
| Q6c: Что произойдёт, если промежуточный шаг упадёт? | Graceful degradation |
| Q6d: Где замыкается петля обратной связи? | Feedback loop |

**Правило:** если в цепочке есть producer (пишет файл, кладёт задачу, генерирует отчёт) — обязан быть consumer (читает, выполняет, доставляет).  
Пока consumer не определён — producer не создавать.

**Пример из жизни:** crystal detect → bridge. Bridge без executor = мёртвая дыра.  
Вместо: detect → bridge → (надежда)  
Надо: detect → execute (что могу) | bridge (что не могу) → bridge executor

**Применение:** запускать Q6a-Q6d при любой задаче, где ты добавляешь новый файл, очередь, отчёт, дата-пайплайн, или системный сервис.

---

## PHASE 3: Tool Mapping

| Вопрос | Цель |
|--------|------|
| Q7: Какие инструменты/модули доступны? | Карта инструментов |
| Q8: Какие skills применить? | Специализированные знания |
| Q9: Нужны ли внешние данные/API? | Dependency check |

---

## PHASE 4: Decomposition Decision

Для текущего узла определить тип:

```
  ┌─ ATOMIC?    → можно выполнить за 1-2 простых действия
  ├─ COMPOSITE? → нужно разбить на подзадачи
  └─ AMBIGUOUS? → не хватает данных → PHASE 5
```

---

## PHASE 5: If AMBIGUOUS

Сгенерировать вопрос пользователю:

```
Для выполнения задачи мне нужно знать: {конкретный вопрос}
```

После ответа → возврат к PHASE 1 (перепроверить клэрити).

**Правила:**
- Один вопрос за раз (не заваливать пользователя списком)
- Максимум 2 вопроса подряд — после второго предлагать «продолжить с тем что есть»
- Если пользователь сказал «делай» / «продолжай» — перевести в COMPOSITE или ATOMIC

---

## PHASE 6: If COMPOSITE

Разбить на подзадачи:
```
1. {subtask_1}
2. {subtask_2}
3. {subtask_3}
```

Для каждой → рекурсивно запустить PHASE 1-4 (depth+1).

**Правила:**
- Максимум 5 подзадач на уровень
- Подзадачи должны быть независимыми (или с явными зависимостями)
- Если подзадач > 5 — объединить связанные или пересмотреть разбивку

---

## PHASE 7: If ATOMIC

Записать выполнимый шаг в формате:

```yaml
- action: {конкретное действие}
  tool: {инструмент}
  input: {входные данные}
  output: {ожидаемый результат}
  estimate: {оценка времени}
```

---

## PHASE 8: Aggregation

Собрать все атомарные шаги в упорядоченный план:

```markdown
## Execution Plan

### Зависимости
- Шаг 2 зависит от шага 1
- Шаг 4 зависит от шага 3

### Шаги
1. {atomic_1}
2. {atomic_2}
...
N. {atomic_N}
```

---

## PHASE 9: Verification Gate

Проверить перед выполнением:

- [ ] Все неопределённости разрешены (нет AMBIGUOUS)
- [ ] Все подзадачи атомарны (нет COMPOSITE)
- [ ] План выполним имеющимися инструментами
- [ ] Глубина рекурсии ≤ 5
- [ ] Понятны критерии успеха для каждого шага
- [ ] Dependency graph корректен (нет циклов)

Если gate не пройден → вернуться к PHASE 4 для неразрешённых узлов.

---

## Стоп-критерии (завершить декомпозицию)

- Все подзадачи атомарны
- Глубина > 5
- Пользователь сказал «продолжай» / «хватит» / «делай» / «далее»
- Пользователь проявил раздражение, сказал «хватит чатиться», «ты завис?» и т.п.
- В user profile указано «fix forward», «не анализировать», «executor, not decider» — в этом случае скилл НЕ ЗАПУСКАТЬ ВООБЩЕ
- AMBIGUOUS не разрешился после 2 вопросов → force COMPOSITE

---

## Паттерны рассуждения (Socratic Reasoning)

Если задача застревает — применить один из 6 паттернов:

| Паттерн | Что делает | Когда применять |
|---------|-----------|-----------------|
| **Transformation** | Переформулировать задачу в похожую | «Какая эта задача на самом деле?» |
| **Decomposition** | Разбить на части | «Из каких частей состоит?» |
| **Regather** | Собрать ключевую инфу | «Что нужно знать для решения?» |
| **Deduction** | Вывести из посылок | «Если А, то Б?» |
| **Verification** | Проверить гипотезу | «А точно это правильно?» |
| **Integration** | Собрать части в целое | «Как части связаны?» |

## Pitfalls

- **КОНФЛИКТ с action-oriented пользователями.** Если в user profile есть «fix forward», «не анализировать», «executor of crystal's will» — этот скилл принесёт ВРЕД. Пользователь будет раздражён вопросами и задержками. Вместо декомпозиции — делай следующий конкретный шаг и показывай результат.
- **Phase 2a (Pipeline Trace) НЕ пропускать при системных изменениях.** Если ты добавляешь новый файл, компонент, очередь или отчёт — ОБЯЗАТЕЛЬНО проверь Q6a-Q6d. Добавление producer без consumer — главный источник мёртвого груза и пользовательского раздражения («а кто это читать будет?»).
- **«Иди по цепочке от начала до конца».** Если пользователь говорит эту фразу — ты пропустил Q6a-Q6d. Остановись, нарисуй pipeline, найди недостающие звенья. Не продолжай писать код пока цепочка не замкнута.
- **Phase 5 (AMBIGUOUS → ask user).** Не задавай вопросы если пользователь уже дал команду «делай» / «далее». Если нужно уточнение — сделай обоснованное предположение и двигайся, а не спрашивай.
- **Не используй этот скилл когда пользователь явно торопится или раздражён.** Фраза «только чатиться мне надоело» — сигнал НЕМЕДЛЕННО прекратить анализ и перейти к действию.

## Пример полного цикла

**Задача:** «Сделай бота для салона красоты»

| Depth | Q | Ответ | Тип |
|-------|---|--------|-----|
| 0 | Что должен уметь бот? | Записывать клиентов, показывать услуги, напоминать | AMBIGUOUS → Q |
| 0 | Через какой интерфейс? | Telegram | AMBIGUOUS → Q |
| 0 | Хранилище? | SQLite | AMBIGUOUS → Q |
| 0 | Нужна админка? | Да, базовую | COMPOSITE → split |
| 1 | Telegram-интеграция | — | ATOMIC |
| 1 | SQLite-схема | — | ATOMIC |
| 1 | Handlers (/start, /services, /book) | — | ATOMIC |
| 1 | Напоминалки | — | ATOMIC |
| 1 | Админ-панель | — | ATOMIC |

**План:**
1. Установить aiogram 3.x
2. Создать SQLite схему
3. handlers: /start, /services, /book, /my_bookings
4. Напоминалки через asyncio
5. Админ-панель /admin
