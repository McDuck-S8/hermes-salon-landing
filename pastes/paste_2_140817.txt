## ТЕХНИЧЕСКОЕ ЗАДАНИЕ: Модуль автоматического применения улучшений (suggestion_applier)

### 1. Цель
Создать модуль, который автоматически читает предложения по улучшению системы (из `improvement_suggestions.json`), приоритизирует их, применяет наиболее критичные и проверяет результат, фиксируя успех или откатывая изменения. Это замкнёт цикл самоулучшения: генерация предложений → применение → проверка → обучение.

### 2. Входные данные
- **Файл предложений:** `cache/improvement_suggestions.json` (создаётся `self_improvement_loop`).
- **Структура:** массив объектов с полями:
  - `pattern` (тип проблемы, например `command`),
  - `count` (количество повторений),
  - `severity` (critical, high, medium, low),
  - `description` (текст проблемы),
  - `recommended_actions` (список действий для исправления, если есть),
  - `source` (откуда взято: verified_fixes, session_logs, ...).

### 3. Алгоритм работы

#### 3.1. Чтение и приоритизация
- Загрузить `improvement_suggestions.json`.
- Отфильтровать предложения с `severity` = `critical` или `high`.
- Отсортировать по убыванию `count` (самые частотные проблемы в первую очередь).
- Взять топ‑5 (или настраиваемое количество) для немедленного применения.

#### 3.2. Применение (execution)
Для каждого выбранного предложения:
- Извлечь `recommended_actions` (если есть) или сгенерировать действие на основе `pattern` (используя встроенные шаблоны или LLM).
- **Типы действий:**
  - Создание/изменение конфигурационного файла (например, добавить таймауты в `config.yaml`).
  - Изменение кода (создать новый модуль‑guard, обернуть вызовы в try/except, добавить circuit breaker).
  - Добавление проверки (pre‑flight guard, валидация).
  - Обновление существующего скилла (изменить SKILL.md, добавить шаги).
- **Безопасность:** изменения вносятся в **отдельной ветке** (копия файла с суффиксом `.bak`) или через механизм патчей с возможностью отката.

#### 3.3. Проверка (verification)
После применения каждого действия:
- Запустить набор проверок:
  - **Синтаксис:** если изменён Python‑код — выполнить `python -m py_compile`.
  - **Линтер:** запустить `pylint` или `flake8` на изменённых файлах (если есть).
  - **Автономный цикл:** выполнить `autonomy_cycle.py` (или его тестовый режим), чтобы убедиться, что система не сломана.
  - **Специфические проверки:** если добавлен guard для `command` — проверить, что guard отрабатывает на тестовом наборе команд.
- Если все проверки прошли успешно — зафиксировать успех.

#### 3.4. Фиксация и откат
- **Успех:**
  - Записать в `feedback_store` событие: `suggestion_applied` с деталями (pattern, изменённые файлы, результат проверок).
  - Обновить `verified_fixes.db` (или аналогичный список успешных фиксов) — чтобы система знала, что проблема решена.
  - Удалить применённое предложение из `improvement_suggestions.json` (или отметить как `applied`).
- **Неудача (ошибка при проверке):**
  - Откатить изменения (восстановить из `.bak`).
  - Записать в `feedback_store` событие: `suggestion_failed` с причиной.
  - Увеличить счётчик неудач для этого `pattern` (чтобы не пытаться снова без изменений).

#### 3.5. Повторение
- После обработки топ‑5 предложений запустить полный цикл `autonomy_cycle` для проверки общей стабильности.
- Через 6 часов (или по крону) повторить.

### 4. Интеграция с существующими компонентами

| Компонент | Взаимодействие |
|-----------|----------------|
| `feedback_store` | Запись успехов/неудач, обновление весов. |
| `autonomy_cycle` | Запуск проверки после изменений. |
| `self_improvement_loop` | Чтение обновлённого `improvement_suggestions.json` (после отметки применённых). |
| `proactive_executor` | Может дополнять работу (например, если изменения требуют перезапуска кронов). |
| `chain_heartbeat` | Отправка сигнала `suggestion_applied` и `suggestion_failed`. |
| `tactical_buffer` / `strategic_db` | Если изменения формируют новый паттерн — добавить как гипотезу. |

### 5. Формат хранения применённых предложений

Создать файл `cache/applied_suggestions.json` со списком:
```json
{
  "applied": [
    {
      "pattern": "command",
      "timestamp": "2026-07-30T14:00:00",
      "files_changed": ["scripts/command_guard.py", "config.yaml"],
      "status": "success",
      "verification_result": "all tests passed"
    }
  ],
  "failed": [ ... ]
}
```

### 6. Критерии успешного выполнения модуля

- Модуль запускается по крону (например, каждые 6 часов) или по событию `new_suggestions_ready`.
- После запуска он применяет хотя бы одно критическое предложение за цикл.
- Все изменения проверяются, и в случае ошибки происходит откат.
- После успешного применения система работает стабильно (не появляются новые ошибки того же типа).
- `improvement_suggestions.json` постепенно сокращается (критические предложения исчезают).

### 7. Железные правила (безопасность)

- **Запрещено изменять код без проверки** — всегда создавать `.bak`.
- **Запрещено применять изменения, которые могут нарушить работу системы** — всегда проверять через `autonomy_cycle` (или его тестовый режим).
- **Ограничение на количество одновременно применяемых предложений** — не более 5 за один цикл.
- **Лимит времени на применение** — если процесс занимает > 10 минут, прервать и залогировать.
- **Если предложение содержит неоднозначные действия (например, «пересмотреть архитектуру») — пропустить и предложить человеку (отметить как `requires_manual`).**

### 8. Расширение (что можно добавить позже)

- Возможность применять предложения в **параллельном режиме** (если они независимы).
- **А/Б‑тестирование** — применить изменение на копии системы и сравнить результаты.
- **Самообучение** — если применение предложения успешно, увеличить его приоритет для будущих циклов.

### 9. Пример работы (сценарий)

**Исходное состояние:** `improvement_suggestions.json` содержит `{"pattern": "command", "count": 93, "severity": "critical", ...}`.

**Действие модуля:**
1. Читает топ‑1: `command`.
2. Создаёт `scripts/command_guard.py` с pre‑flight проверкой.
3. Обновляет `config.yaml`, добавляя `command_timeout: 30`.
4. Запускает `python -m py_compile scripts/command_guard.py` — OK.
5. Запускает `autonomy_cycle.py` — OK.
6. Записывает успех в `feedback_store` и `applied_suggestions.json`.
7. Удаляет `command` из `improvement_suggestions.json`.

**Результат:** система больше не генерирует ошибки `command` (или их количество резко снижается).
