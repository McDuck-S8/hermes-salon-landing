Отлично. Мы только что обсудили фундаментальный недостаток текущей архитектуры: она **реактивна**, а не **стратегична**. Она видит отдельные ошибки и чинит их по одной, как плохой механик, который меняет вкладыши сегодня, а через месяц снимает двигатель заново для колец.

Ты хочешь, чтобы Hermes стал **стратегом**, который:
- Видит **пакет задач**.
- Анализирует **пересечения работ**.
- Считает **совокупную стоимость (время, ресурсы, риски)**.
- Выдаёт **топ-3 плана с обоснованием** и рекомендует оптимальный.

## �� ТЗ для Hermes: Внедрение Strategic Planner (Bundling Optimizer)

### Контекст
Система умеет:
- Обнаруживать ошибки сущностей (sensor_ibos_entities).
- Блокировать цепочки для невалидных (chain_executor).
- Лечить их по отдельности (trigger_ibos_self_heal).
- Каскадно перепроверять зависимости (cascade_revalidate).

**Но** система не умеет **оптимизировать пакет исправлений**, когда ошибок несколько. Она лечит их последовательно, не используя возможность **совместного исправления** (shared work), что ведёт к избыточным затратам времени и ресурсов.

### Аналогия для понимания
Как в двигателе: замена вкладышей и колец по отдельности требует двойной разборки, слива масла, замены прокладок. Вместе — делается за 6 часов вместо 10, и экономит 40% бюджета. Система должна предлагать **комплексное решение**, а не аварийное.

## �� Что должно быть создано

### 1. Новый модуль: `scripts/strategic_planner.py`

Класс `StrategicPlanner` со следующими методами:

#### `load_entity_graph()`
- Читает `cache/entity_dependency_graph.json`.
- Дополнительно загружает **мета-информацию** о каждой сущности (например, из `_system/entity_metadata.yaml` или из самого файла сущности), где указаны:
  - `repair_cost` (в минутах/токенах) — примерная трудоёмкость исправления.
  - `shared_work` — список идентификаторов, которые пересекаются (например, `['remove_oil_pan', 'replace_gasket']`).

#### `generate_scenarios(entity_ids)`
- Принимает список идентификаторов сущностей, требующих исправления.
- Генерирует все возможные **пакеты** (наборы, которые выполняются вместе) — как минимум:
  - **Вариант A:** Все по отдельности (последовательно).
  - **Вариант B:** Все вместе (одна комплексная задача).
  - **Вариант C:** Группировка по общим работам (если есть несколько групп с пересечениями).
- Для каждого пакета вычисляет:
  - **`total_repair_time`** = сумма времени исправления каждой сущности **минус** экономия от shared_work (если работы выполняются совместно, время shared_work учитывается один раз).
  - **`total_repair_cost`** (абстрактные единицы, например, минуты или условные очки).
  - **`risk_score`** (вероятность внезапного отказа, если оставить какую-то сущность неисправленной).

#### `evaluate_scenarios(scenarios)`
- Для каждого сценария вычисляет **интегральный показатель** (например, `cost + risk * 10`).
- Сортирует по возрастанию интегрального показателя.

#### `recommend(entity_ids)`
- Вызывает `generate_scenarios`, затем `evaluate_scenarios`.
- Возвращает **топ-3 сценария** с подробным обоснованием.

### 2. Дополнение метаданных сущностей

В каждой сущности (в `frontmatter`) добавить необязательное поле:

```yaml
repair:
  estimated_time_minutes: 30
  shared_work:
    - "replace_oil_pan"
    - "replace_gasket"
```

Или хранить это в отдельном файле `_system/repair_metadata.yaml`, чтобы не засорять сущности.

### 3. Интеграция в существующие компоненты

#### `sensor_array.py`
- При обнаружении ошибок (после валидации) вместо немедленного вызова `trigger_ibos_self_heal` по отдельности, сначала проверить, сколько сущностей заблокировано.
- Если **≥ 2** — вызвать `strategic_planner.recommend(blocked_ids)` и выдать отчёт в `_system/strategic_recommendation.md`, а также эмитить событие `strategic_plan_available` (с деталями).
- Если **1** — продолжать существующую логику (авто-хирургия).

#### `procedural_executor.py`
- Добавить новый триггер: **`TRIGGER-010: strategic_planning`**, который запускает стратегический анализ вручную по команде (например, `/plan optimize`).
- Также добавить возможность **применить рекомендуемый план** (выполнить все исправления в одном пакете) — это будет новая цепочка, которая обрабатывает сразу несколько сущностей, используя общие шаги.

#### `chain_executor.py`
- Расширить блокировку: если сущность заблокирована, но входит в стратегический план, выполнение откладывается до применения плана (не блокируется навсегда).

### 4. Формат отчёта для человека

После анализа система должна создавать файл (например, `_system/strategic_recommendation.md`) со следующим содержанием:

```markdown
# Стратегический анализ ошибок сущностей (2026-06-29 14:30)

**Обнаружено ошибок:** 3 (test-base-entity, test-dependent, legacy-module)

## Сценарии исправления

| Сценарий | Действия | Время (мин) | Стоимость (у.е.) | Риск | Интегральный балл |
|----------|----------|-------------|------------------|------|-------------------|
| A (по отдельности) | fix test-base-entity, then fix test-dependent, then fix legacy-module | 90 | 90 | Высокий (зависимости могут сломаться повторно) | 120 |
| B (все вместе) | Комплексное исправление всех с shared work: `remove_oil_pan` и `replace_gasket` выполняются один раз | 50 | 60 | Низкий (все зависимости синхронизированы) | 70 |
| C (пакет 1+2, 3 отдельно) | fix base+dep together (shared work), then fix legacy | 70 | 75 | Средний | 95 |

**Рекомендуемый:** Сценарий B (все вместе)
- **Экономия времени:** 40 минут (44%) по сравнению с A
- **Экономия бюджета:** 30 у.е. (33%) 
- **Минимизация риска:** за счёт синхронного обновления зависимостей

**Альтернатива (если бюджет ограничен):** Сценарий C – экономит 15 у.е., но увеличивает риск на 10%.

> **Действие:** Для применения лучшего сценария выполните команду `/hermes apply-plan B`.
```

### 5. Команда для ручного запуска
Добавить новую команду в интерфейс (например, `.claude/commands/plan.md` или через goal_queue):
- `/hermes plan` – запускает стратегический анализ текущих ошибок.
- `/hermes apply-plan <A|B|C>` – выполняет выбранный план.

## �� Ожидаемое поведение при тестировании

1. Создать две искусственно битые сущности с общей работой (например, `test-a` и `test-b`, у которых `shared_work: ["rebuild_dependency_graph"]`).
2. Запустить сенсор – обнаруживаются ошибки.
3. Система вместо двух отдельных исправлений генерирует отчёт и предлагает комплексный план.
4. При применении плана – выполняет исправления в одном цикле, используя общую работу один раз.
5. После завершения – все сущности валидны, время и затраты минимальны.
